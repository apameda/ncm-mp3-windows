# Windows 绿色版打包

构建目标为 Windows 10/11 x64，用户解压 ZIP 后双击 `NCM批量转MP3.exe`，不需要安装 Python、Node.js 或 FFmpeg。软件转换时只使用本地文件与随包 FFmpeg；以下下载仅发生在开发者构建阶段。

## 构建环境与命令

- macOS 或 Linux；Node.js 20 或更新版本；系统 `unzip`。不使用 npm 运行时依赖、Wine、全局打包器或 Windows 编译器。
- 在项目根目录运行 `node scripts/package-windows.mjs`。首次构建从下列固定上游下载依赖；后续复用 `.cache/windows` 内经过同样 SHA-256 检查的缓存。
- 完全离线构建：先放齐下表的四个文件，再运行 `node scripts/package-windows.mjs --offline`。其他显式缓存目录可用 `--cache-dir /absolute/cache/path` 指定。
- 输出 `dist/NCM批量转MP3-Windows-x64.zip` 与同名 `.sha256`。脚本先对 ZIP 内所有条目做完整性检查，再交付最终文件。构建中间文件自动清理。
- ZIP 写入器的离线自检：`node scripts/verify-zip.mjs`，覆盖 UTF-8 中文路径、空文件、分块二进制及解压 CRC 检查。

## 包结构与许可

按 [Electron 官方手动打包方法](https://www.electronjs.org/docs/latest/tutorial/application-distribution)将应用放入 `resources/app` 并重命名 `electron.exe`。全部 DLL、ICU 数据、V8 快照、locale 与 Chromium 资源均保留，不仅复制 EXE。

```text
NCM批量转MP3-Windows-x64/
  NCM批量转MP3.exe
  LICENSE-electron
  LICENSES.chromium.html
  README.md
  THIRD_PARTY_NOTICES.md
  第三方源码.md
  RELEASE_NOTES.md
  LICENSE
  BUILD-MANIFEST.json
  docs/
    第三方源码.md
    测试记录.md
    screenshots/
  licenses/ffmpeg/{LICENSE,README.txt}
  resources/app/
    package.json
    src/
    resources/ffmpeg.exe
    README.md
    THIRD_PARTY_NOTICES.md
    第三方源码.md
    LICENSE
  ...完整 Electron 运行环境
```

Electron 自身采用 MIT 许可，保留发行包原始 `LICENSE` 为 `LICENSE-electron`，并保留 Chromium 等组件完整声明。Gyan 明确将其静态构建标为 GPLv3；打包时逐字保存其原始 `LICENSE` 和 `README.txt` 到 `licenses/ffmpeg/`。FFmpeg 9.0.2 的上游源码定位为 [946fcce07b](https://github.com/FFmpeg/FFmpeg/commit/946fcce07b)。[第三方源码指引](第三方源码.md)列出原始构建配置、37 项依赖版本、官方源码入口与尚未核实的材料；它不声称是完整的 Corresponding Source 归档。

打包脚本将整个 `docs/` 目录复制到发行包根目录，保留 README 的截图和说明链接；同时把源码指引复制为根目录和 `resources/app/` 下的 `第三方源码.md`，并在根目录附上 `RELEASE_NOTES.md`。本项目自己的应用源代码随绿色版交付；第三方源码仍按指引定位，本脚本不会额外下载或打包完整第三方源码树。

## 验证边界

打包脚本可在 macOS 验证归档校验值、内容布局与 ZIP 完整性，但不会执行 Windows EXE。Windows 端还需完成一次解压启动、中文路径批量转换、取消与失败继续的实机验收。当前包未签名，不宣称通过代码签名或 SmartScreen 信誉验证。


## Windows 与 Mac 统一打包入口

2026-10-16 新增 `scripts/package.mjs`，使用与 QQ 项目同一套已经验证的三平台组装流程。应用源代码始终只读取本 NCM 项目，复用的仅是名称和固定 SHA-256 均匹配的第三方运行环境归档。原 `scripts/package-windows.mjs` 保留兼容，继续生成 Windows 包；两入口不可同时运行并写入相同 `dist/` 文件。

在 macOS 构建机使用 Node.js 20 或更新版本，以及系统自带 `unzip`、`ditto`、`plutil`、`lipo`、`otool`、`codesign`：

```sh
node scripts/package.mjs --target all --offline
node scripts/package.mjs --target darwin-arm64 --offline
node scripts/package.mjs --target darwin-x64 --offline
node scripts/package.mjs --target win32-x64 --offline
```

省略 `--target` 时依次生成全部三平台；省略 `--offline` 时才允许从下文固定上游补充缺失缓存。Windows 运行目标为 Windows 10/11 x64；所用 Electron 44.7.2 的 Mac 最低系统为 macOS 13.0。

| 目标 | ZIP | 默认保留的解压目录 |
|---|---|---|
| Windows x64 | `dist/NCM批量转MP3-Windows-x64.zip` | `dist/NCM批量转MP3-Windows-x64/` |
| Mac Apple Silicon | `dist/NCM批量转MP3-macOS-arm64.zip` | 系统临时目录中的 `ncm-mp3-unpacked-darwin-arm64-*/NCM批量转MP3-macOS-arm64/NCM批量转MP3.app` |
| Mac Intel | `dist/NCM批量转MP3-macOS-x64.zip` | 系统临时目录中的 `ncm-mp3-unpacked-darwin-x64-*/NCM批量转MP3-macOS-x64/NCM批量转MP3.app` |

每份 ZIP 附同名 `.sha256`，日志输出解压目录的准确绝对路径；`--no-unpacked` 只保留 ZIP。新脚本默认缓存为本项目 `.cache/package/`，可用 `--cache-dir /absolute/path` 更改；依次只读复用同目录文件、相邻 QQ 项目 `../qq-mp3-desktop/.cache/package/` 中名称匹配文件，以及本项目旧 `.cache/windows/` 中 Windows Electron、官方清单和 Gyan Windows FFmpeg。缓存复用也必须通过固定哈希；不修改兄弟项目，不复制兄弟项目的源码、界面或业务资源。

Mac Electron 使用同一官方发行的两个归档，缓存文件名与官方下载文件名相同：

| 归档 | 审核固定 SHA-256 |
|---|---|
| `electron-v44.7.2-darwin-arm64.zip` | `07d73d3d6dd0b8679c2f1849e30df179ea50c1d6b17630fcc398ae05221f0bd2` |
| `electron-v44.7.2-darwin-x64.zip` | `915cb638692e3595926fa64903ee0562c3c0c5a1febb84724175756ca2f0f3b7` |

下载前缀为 `https://github.com/electron/electron/releases/download/v44.7.2/`。脚本同时对照同版 `SHASUMS256.txt`（缓存名 `electron-v44.7.2-SHASUMS256.txt`）与上述固定哈希；Windows 仍使用前文相同官方归档和校验值。来源为 [Electron 官方发行](https://github.com/electron/electron/releases/tag/v44.7.2)。

### 共用检查与许可原文

脚本用 `lipo` 核对 Mach-O 架构，用 `otool -L` 检查 FFmpeg 仅依赖系统动态库；发现外部路径依赖即停止。还对实际程序内的编译配置做静态检查，拒绝包含 `--enable-nonfree` 或无法定位配置的二进制。这些静态检查不等同于在另一架构上执行程序。

完整 GPLv3 文本可从 ffmpeg-static 固定发行的 `linux-arm.LICENSE` 资产取得并缓存为 `GPL-3.0.txt`，校验值为 `8ceb4b9ee5adedde47b31e975c1d90c73ad27b6b165a1dcd80c7c545eb65b903`；若本机已有已校验 Gyan ZIP 内完全相同的许可原文则只复用该文本。该资产只作为通用许可证原文，不包含 Linux 程序。Intel 原始许可摘要另以 `LICENSE.md` 保留。

## App 结构、签名与验收边界

Windows 保留完整 Electron DLL、locale、ICU 和 V8 资源，主程序重命名为 `NCM批量转MP3.exe`。Mac 主包重命名为 `NCM批量转MP3.app`，主可执行文件同名；修改 `CFBundleIdentifier` 为 `com.local.ncmmp3`，并同步主版本、显示名称和辅助 App 的标识。FFmpeg 位于应用源根目录的 `resources/ffmpeg` 或 `resources/ffmpeg.exe`。

Mac 先对包内 Mach-O 与嵌套 App/Framework 从内到外做本地 ad-hoc 重签名。原始代码存在签名时保留其 entitlements，不杜撰新的 entitlement；随后执行 `codesign --verify --deep --strict`。签名信息、来源哈希及重签名后的二进制哈希记入 `BUILD-MANIFEST.json`。

Mac 在系统临时目录中组装、签名、创建 ZIP 并验证，再将最终 ZIP 搬到项目 `dist/`；原生验收 App 也留在系统临时目录。这样避免项目所在 CloudStorage 文件提供方在签名期间重新附加 Finder 元数据。仅对新组装 App 清除与签名不兼容的 `com.apple.FinderInfo` 和 `com.apple.ResourceFork`，保留 quarantine 和系统信任设置。

Mac ZIP 使用系统 `ditto -c -k --sequesterRsrc --keepParent`，保留 App 可执行权限和 Framework 符号链接。归档完成后先完整解压复验，再检查严格签名、主程序与 FFmpeg 可执行权限、Framework 符号链接和目标架构，通过后才交付 ZIP。Windows ZIP 使用 Node 内建流式写入器，明确设置中文文件名 UTF-8 标志。

本地 ad-hoc 签名验证不等于 Apple Developer ID 签名、公证或 Gatekeeper 放行；此脚本不上传 Apple 服务，不宣称已通过这些分发检查。ARM App 可在本机实际启动验证；Intel Mac 与 Windows 包在缺少相应实机运行时只能完成归档、来源与布局检查，不能写成已做实机验收。
